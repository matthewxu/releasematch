## 上线后更新节奏（定稿建议）

原则：**库与测速靠 cron 自动；页面靠增量 bake；模板/SEO/跟踪脚本变更才全量 prepare+deploy。**

### A. 自动（尽量不人工）

| 频率 | 动作 | 落点 | 说明 |
|------|------|------|------|
| 每 6h | 测速 cron | VPS `speedtest_batch_worker --all-published` | TTL 内 skip；刷新 `slot_speed_summary` |
| 每 6h+30m | **增量发布** | `incremental_publish_worker` | 脏页 → bake dist；**正式期应带上传**（勿长期 `--prepare-only`） |
| 每日 06:30 | TMDB 日同步 | `ops tmdb-sync` | 选槽库新鲜度 |

> 若增量 cron 仍是 `--prepare-only`：上线后须改为实际上传（或等价 Ops Deploy 增量），否则公网页会落后于 MySQL。

### B. 每日人工（~10 min）· Ops ⑥

对照 [每日巡检检查清单](../../checklists/daily/每日巡检检查清单.md)：

1. Ops ⑥「刷新巡检」或 CLI：`torrent_sources.run status` + `db status`
2. 测速覆盖：有 Rec 缺 summary →「测速缺口补测」
3. TMDB 新鲜：`export_date` ≤ 3 天
4. 看 cron 日志尾（本机/VPS）：无连续 traceback
5. 若昨日有扩槽/改模板：确认已 generate（或依赖增量 worker）

### C. 每周人工（~30 min）

对照 [每周例行检查清单](../../checklists/daily/每周例行检查清单.md)：

1. `poc_phase0` 四源
2. VPS `docker ps` Jackett / FlareSolverr
3. `failed_slots_merge_reports.py --list-active`
4. GSC：覆盖率 / 错误页 / 新 sitemap 是否消化
5. Clarity：异常会话 / 错误页抽样（可选）

### D. 变更驱动（按需）

| 变更类型 | 动作 | Deploy？ |
|----------|------|---------|
| 扩槽 / 修单页数据 | Ops ③ Pipeline→Generate→Speedtest（或一键流程）→ ④ 增量 Deploy | 是（增量） |
| 模板 / i18n / Trust / base.html | `generate all` + `seo_c2` + 全量 Deploy | 是（全量） |
| **仅改 tracking.js** | Ops ⑤ 保存并同步 → **只上传 `static/js/tracking.js`**（或增量/全量带 static） | 是（静态即可） |
| Indexer / 评分规则大变 | `refetch-all` → generate all → seo_c2 → Deploy | 是（全量） |
| 发版前 | [发版前回归](../../checklists/daily/发版前回归检查清单.md)（BB S04E06） | 通过后再 Deploy |

### E. 两周 / 月度（建议）

| 频率 | 动作 |
|------|------|
| 每 2 周 | 抽 5 个 sitemap 页：Rec 仍在、测速未过期（>72h 排复测）、无 5xx |
| 每月 | 回顾失败槽类型占比；收录率是否达到启动 C4（+50 页/周）门槛（手册：收录 &lt;25% 不扩） |
| 开放爬取后 7～14 天 | GSC 首次收录数 / 未编入索引原因；按需微调 title/内链 |

### F. 节奏一览（可贴看板）

```
自动  6h     测速 TTL
自动  6h+30m 增量 bake（+上传）
自动  日     TMDB sync
人工  日     Ops⑥ 巡检 10min
人工  周     PoC · VPS · 失败槽 · GSC 30min
按需  扩槽   Ops ①→④ 增量发版
按需  模板   generate all + seo_c2 + 全量发版
按需  跟踪JS 只同步 tracking.js
月度  收录   决定是否启动 C4 扩页
```
